# DSC-V3-011: Integrate and qualify the final DSC v3 release

## Lifecycle and entry criteria

Read all authoritative DSC v3 documents and the Outcomes of DSC-V3-001 through
DSC-V3-010 plus DSC-V3-012. Update metadata and record the integration baseline
before editing.
Every required decision must be accepted and all dependency outcomes complete.
Use Modern Go guidance for Go changes, preserve unrelated worktree changes, and
keep GC last.

  listed in `../PLAN.md` and Tasks 001-01 through 001-05.

## Objective

Integrate the approved v3 schema, conversion, admissions, and component
projections; eliminate inconsistent generated/test artifacts; and provide final
fresh-install, upgrade, compatibility, retry, rollback, ODH, and RHOAI evidence.
This is the task that implements and executes the consolidated E2E coverage
handed off by Tasks 001 and 006-009/012.

## Final required state

- V3 is the hub, sole storage version, and only typed DSC version used by
  production reconciliation, registries, modules, status writers, utilities,
  generators, and primary samples.
- V2 is `served: true`, `storage: false`, `deprecated: true`, has the accepted
  API-version warning, version-correct admissions, and semantic v2 <-> v3
  conversion, including DEC-024's accepted normalization and reserved
  metadata lifecycle.
- V1 API code, conversion, admissions, scheme/PROJECT registration, samples,
  generated serving, bundle content, and production references are absent.
- `/convert` is registered through v2 and uses ConversionReview protocol
  exactly `[v1]`.
- Dashboard, AI Hub, Feature Store, and Data Registry implement the accepted
  lifecycle, projection, status, conditions, and v2 compatibility contracts.
- V3 exposes MaaS only at `aigateway.modelsAsAService`; v2 legacy KServe MaaS
  converts with unchanged DEC-022 forward precedence and DEC-024's literal
  `legacy-managed` marker, derived only from incoming v2 L=Managed. Reverse
  keeps C/A migrated and sets L=Managed iff marked, else Removed including empty.
  Custom field warnings are absent; the existing v2 CEL contract remains.
- V3 UPDATE compares old/new canonical, KServe parent, and AI Gateway parent
  management states; any change permanently deletes the marker, even if later
  reverted. Otherwise `OldObject` is authoritative. Native CREATE strips
  supplied reserved metadata. Reject unknown marker values. V2 ignores incoming
  markers and resets from current L. Reuse componentApi value types without
  canonical pointers or duplicated wrappers; original C/A/absence are not
  restored and there is no JSON payload or snapshot. OpenAPI remains unchanged.
- Internal AI Hub/Model Registry and Data/Feast identities remain unchanged;
  DCH is absent.
- Every v2/v3 OpenAPI difference is explicit and paired with direct and both
  round-trip tests; future unlisted differences fail the guard.

## Integration work

1. Review dependency diffs and Outcomes for overlapping types, conversions,
   defaults, validators, status aggregation, generated patches, and fixtures.
2. Search all production code for v1 and typed-v2 usage. V1 has no production
   allowlist. V2 is allowed only for conversion, v2 admission, compatibility,
   deprecation, and explicit upgrade tests; record each remaining hit.
3. Regenerate and review ODH/RHOAI CRDs, webhook configuration, bundles/CSVs,
   RBAC if affected, API docs, deepcopy/object code, and v3 samples.
4. Verify identical unchanged semantics across platform variants and exact
   accepted differences where build-specific behavior is required.
5. Resolve only integration defects. Record a new decision rather than
   choosing behavior if dependency contracts conflict.

## Acceptance matrix

- Whole-object v2/v3 direct and round-trip conversion, including DEC-024's
  migrated C/A, legacy empty -> Removed, and explicit marker retirement
  expectations, reserved/unrelated metadata handling, status, conditions,
  releases, related objects, deprecated inputs, empty values, and every
  transformed stanza.
- Real `/convert` single/multiple-object requests and v2 read-modify-write
  preservation of all v3-only values.
- V2/v3 defaults, validations, applicable warnings, immutability, updates, and
  singleton behavior, including absence of the removed custom MaaS warning.
- Component lifecycle and status for all accepted Dashboard, AI Hub, and Data
  state combinations, including idempotent removal.
- KServe/MaaS E2E proves DEC-022 forward precedence, all three handler
  outcomes, v2 CEL, v3 canonical-only shape, and DEC-024 normalization and
  permanent retirement, including the Task 012 handoff below.
- ODH and RHOAI fresh installation.
- Every supported-source upgrade through DSC-V3-010's pre-upgrade gate,
  post-upgrade v3 rewrite, storedVersions cleanup, retry, and rollback boundary.
- A future-v3-change negative test showing an unlisted schema difference fails.

## Task 012 cluster scenario handoff

Task 012 supplies unit/envtest/integration evidence; this task owns the new
E2E implementation and ODH/RHOAI execution. Only compile fixture fixes may
land in E2E code during Task 012. The scenario is specified now; implementation
and execution evidence are pending.

1. Seed supported v2 legacy-only and conflicting MaaS fixtures with legacy
   `Managed` through an allowed create/source-release path; do not bypass or
   weaken the retained v2 transition guard. Include absent canonical stanza
   and schema-defaulted `{}`, plus the originally empty AI Gateway parent case
   at the appropriate direct-conversion/integration layer.
2. Read through v3 and verify canonical projection and the three handler
   outcomes. Read through v2 and verify C/A remain migrated, legacy Managed
   returns iff marked, and unmarked legacy becomes Removed. Include source
   L=Managed with canonical Removed or unmanaged KServe to prove marker creation
   is independent of effective enablement. Conversion/integration fixtures must
   cover legacy empty -> Removed and no restoration of original C/A/absence.
3. Make unrelated v2/v3 spec, metadata, and status updates and verify
   marker preservation. Check stale incoming reserved annotations cannot override
   current v2 L; native v3 CREATE strips supplied reserved metadata and UPDATE
   uses the old marker regardless of new-object annotation edits.
4. Independently change canonical management state and each parent management
   state through v3, then verify marker retirement and a v2 view with current
   canonical state and legacy `Removed`. Revert each edit in a later update and prove original
   legacy intent cannot return. Verify v2 `Removed -> Managed` remains rejected.
5. Retain unknown-marker-value rejection evidence from Task 012's
   conversion/admission integration tests and cover relevant real-cluster
   behavior without claiming user-supplied annotations are stored authority.
   Verify absence of custom MaaS field warnings and preservation of the v2
   API-version warning.

There is no supported installed intermediate-v3 release carrying the legacy
KServe field. Use supported v2 sources, with Task 010's separate upgrade gate
where required; do not create an intermediate-v3 compatibility obligation.
