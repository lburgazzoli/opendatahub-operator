# DSC-V3-011: Integrate and qualify the final DSC v3 release

## Lifecycle and entry criteria

Read all authoritative DSC v3 documents and the Outcomes of DSC-V3-001 through
DSC-V3-010. Update metadata and record the integration baseline before editing.
Every required decision must be accepted and all dependency outcomes complete.
Use Modern Go guidance for Go changes, preserve unrelated worktree changes, and
keep GC last.

## Objective

Integrate the approved v3 schema, conversion, admissions, and component
projections; eliminate inconsistent generated/test artifacts; and provide final
fresh-install, upgrade, compatibility, retry, rollback, ODH, and RHOAI evidence.

## Final required state

- V3 is the hub, sole storage version, and only typed DSC version used by
  production reconciliation, registries, modules, status writers, utilities,
  generators, and primary samples.
- V2 is `served: true`, `storage: false`, `deprecated: true`, has the accepted
  warning, version-correct admissions, and lossless v2 <-> v3 conversion.
- V1 API code, conversion, admissions, scheme/PROJECT registration, samples,
  generated serving, bundle content, and production references are absent.
- `/convert` is registered through v2 and uses ConversionReview protocol
  exactly `[v1]`.
- Dashboard, AI Hub, Feature Store, and Data Registry implement the accepted
  lifecycle, projection, status, conditions, and v2 compatibility contracts.
- Internal AI Hub/Model Registry and Data/Feast identities remain unchanged;
  DCH is absent.
- Every v2/v3 OpenAPI difference is explicit and paired with direct and both
  round-trip tests; future unlisted differences fail the guard.

## Integration work

1. Review dependency diffs and Outcomes for overlapping types, conversions,
   defaults, validators, status aggregation, generated patches, and fixtures.
2. Search all production code for v1 and typed-v2 usage. V1 has no production
   allowlist. V2 is allowed only for conversion, v2 admission, compatibility,
   deprecation, and explicit upgrade tests; record each remaining hit.
3. Regenerate and review ODH/RHOAI CRDs, webhook configuration, bundles/CSVs,
   RBAC if affected, API docs, deepcopy/object code, and v3 samples.
4. Verify identical unchanged semantics across platform variants and exact
   accepted differences where build-specific behavior is required.
5. Resolve only integration defects. Record a new decision rather than
   choosing behavior if dependency contracts conflict.

## Acceptance matrix

- Whole-object v2/v3 direct and round-trip conversion, including metadata,
  status, conditions, releases, related objects, deprecated inputs, empty
  values, and every transformed stanza.
- Real `/convert` single/multiple-object requests and v2 read-modify-write
  preservation of all v3-only values.
- V2/v3 defaults, validations, warnings, immutability, updates, and singleton
  behavior.
- Component lifecycle and status for all accepted Dashboard, AI Hub, and Data
  state combinations, including idempotent removal.
- ODH and RHOAI fresh installation.
- Every supported-source upgrade through DSC-V3-010's pre-upgrade gate,
  post-upgrade v3 rewrite, storedVersions cleanup, retry, and rollback boundary.
- A future-v3-change negative test showing an unlisted schema difference fails.

## Required gates

Run focused suites plus:

```bash
make generate manifests api-docs
make fmt
make lint
make unit-test
make build
git diff --check
```

Run the implemented ODH and RHOAI E2E/upgrade jobs on supported clusters. Local
cluster absence may defer execution to CI but not test implementation; record
the exact job, environment, and expected assertions.

## Definition of done

All final-state and acceptance-matrix entries are proven; generated output is
reviewed and reproducible; no proposed decision is encoded; task/decision
records reflect outcomes; no unresolved dependency or unexplained compatibility
allowlist remains; and all required gates pass or have recorded CI evidence.
