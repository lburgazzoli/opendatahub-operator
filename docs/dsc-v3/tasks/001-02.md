# DSC-V3-001-02: Atomically cut over to v3 and remove v1

## Lifecycle and scope

Read the authoritative local documents, `001.md`, and the completed
`001-01.md` Outcomes. Update this file's metadata and Outcomes on start. Follow
DEC-002 through DEC-007 and DEC-014. V2 and v3 are schema-identical in this
subtask; conversion therefore preserves the complete object without
transforming fields.

## Implementation

1. In one compiling change, move `conversion.Hub` and
   `+kubebuilder:storageversion` from v2 to v3, make v2 the
   `conversion.Convertible` spoke, and implement explicit typed
   `ConvertTo`/`ConvertFrom` against the v3 hub. Do not leave a commit where v3
   is the hub but v2 conversion is absent.
2. Copy metadata, spec, and status semantically unchanged. Do not use JSON
   serialization, `unsafe`, defaulting, validation, normalization, logging-based
   recovery, cluster access, or proposed field mappings.
3. Register controller-runtime `/convert` using the v2 DSC type before removing
   the v1 registration later in this same atomic change.
4. Add distinct `DataScienceClusterV2` and `DataScienceClusterV3` GVK constants
   and bind each admission path to its own GVK.
5. Add v3 defaulting and validation by porting identical v2 rules. Preserve v2
   admissions independently.
6. Generate conversion configuration with
   `conversionReviewVersions: [v1]`; this is the Kubernetes protocol version,
   not a DSC served-version list.
7. Replace/adapt `pkg/dsc/compare/v2only.go` with a normalized v2/v3 OpenAPI
   guard covering paths, types, requiredness, nullability, defaults, enums, CEL,
   and list/map semantics. Its initial expected-difference set is empty.
   Define the shared machine-readable registry now: every future inventory
   entry has a stable `case_id`, v2/v3 paths, changed semantics, and executable
   forward, backward, v2-round-trip, and v3-round-trip cases. The guard fails
   when any category is missing or was not executed by the shared runner.
8. In that same compiling change, remove the v1 API and converter, scheme and
   PROJECT entries, admissions, webhook registration, GVK/constants, and
   compiled v1 consumers. The current v1 converter asserts that v2 is the hub,
   so it must not remain after the v3 hub switch. Do not create a temporary
   v1 <-> v3 converter.
9. Port useful v1-located behavior tests to v2/v3 compatibility tests. Inventory
   `conversion.opendatahub.io/aigateway-state`; delete it only if no remaining
   consumer needs it.
10. Regenerate and assert the CRD moves storage from v2 to v3, removes v1, and
    activates v2 conversion atomically.

## Tests

- Direct v2 -> v3 and v3 -> v2 equality with all metadata, components,
  deprecated fields, status, conditions, releases, and related objects filled.
- Both whole-object round trips, repeated-conversion idempotence, and empty,
  absent, `Managed`, and `Removed` values.
- Negative one-hop cases so inverse but mutually wrong mappings cannot pass by
  cancellation.
- Real `/convert` ConversionReview requests in both directions with one and
  multiple objects, including status and metadata preservation.
- Independent v2/v3 defaulting, validation, GVK, singleton, warnings, and
  update tests.
- OpenAPI guard negative tests proving each supported semantic category is
  detected.
- Registry negative tests proving an inventory entry without all four executed
  conversion categories fails.

## Definition of done

The atomic hub/storage/v1-removal cutover compiles without a transitional
v1 <-> v3 converter; the real conversion endpoint losslessly handles v2/v3
objects; version-specific admissions remain correct; `[v1]` is the only
ConversionReview protocol entry; and the OpenAPI guard prevents silent future
differences. Run all focused tests and mandatory Make gates; record exact
results.
