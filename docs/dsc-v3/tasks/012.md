# DSC-V3-012: Migrate KServe MaaS configuration

## Lifecycle and authority

Read `../development.md`, `../decisions.md`, `../PLAN.md`, `../TASKS.md`, and
the completed DSC-V3-001 Outcomes. On start, set `status: in_progress`,
`start_date`, `assignee`, and `last_updated`, and populate Execution Outcomes.
On completion, record results, set `status: completed`, and set `end_date` and
`last_updated`.

DEC-022's forward precedence and accepted DEC-024's literal-marker/admission
contract are the conversion authority; DEC-024 supersedes DEC-022's reverse
policy and specifies the accepted normalization. DEC-023 defines the
integration-first test boundary. No component Jira resolution or additional product feedback is an
entry condition. If code reality conflicts with the accepted decisions,
record a new proposed decision and stop only the conflicting part; do not
silently choose different conversion behavior.

## Objective

Remove deprecated `spec.components.kserve.modelsAsService` from the v3 wire
schema and make `spec.components.aigateway.modelsAsAService` the only v3 MaaS
configuration. Keep the v2 API shape unchanged and served, remove the custom
MaaS field deprecation warnings, retain its existing update validation unless a
separate accepted decision changes it, and move existing runtime fallback
semantics into deterministic v2 <-> v3 conversion.

This task changes KServe/MaaS conversion,
reserved-annotation admission, custom field warnings, and the runtime fallback
made obsolete by conversion. KServe lifecycle, all other KServe fields,
AI Gateway Batch Gateway behavior, MaaS status, and condition names remain
unchanged.

There is no supported installed intermediate-v3 release exposing the old
KServe MaaS field. Do not add compatibility machinery for that development-only
shape; supported legacy sources enter through v2. Task 010's upgrade gates are
unchanged. Implementation and verification evidence are recorded below.

## Accepted conversion contract

### V2 to v3

1. Copy every KServe and AI Gateway field except the removed v3 KServe
   `modelsAsService` field.
2. If v2 `aigateway.modelsAsAService.managementState` is non-empty, copy it to
   v3 unchanged. It wins over a conflicting deprecated KServe value.
3. Otherwise, when v2 `kserve.managementState` is `Managed`, copy v2
   `kserve.modelsAsService.managementState` to v3
   `aigateway.modelsAsAService.managementState`, including the empty value.
   When KServe is not `Managed`, leave the canonical v3 MaaS state empty. This
   is the same gating used by today's runtime fallback.
4. Copy `aigateway.managementState` unchanged, except when the existing runtime
   fallback would enable AI Gateway: if it is empty while both
   `kserve.managementState` and `kserve.modelsAsService.managementState` are
   `Managed`, set v3 `aigateway.managementState` to `Managed`.
5. Do not default or normalize any other empty state in conversion. Under
   DEC-010 its effective value remains `Removed`.
6. Ignore the incoming `conversion.opendatahub.io/maas-v2-state` annotation.
   Set its value to literal `legacy-managed` if and only if visible source
   legacy `L` is `Managed`, regardless of canonical precedence or effective
   enablement. Otherwise remove it, including for empty `L`.

The MaaS-state selection is equivalent to this table. `C` is v2
`aigateway.modelsAsAService.managementState`, `K` is v2
`kserve.managementState`, and `L` is v2
`kserve.modelsAsService.managementState`.

| C | K | L | v3 canonical MaaS state | Reason |
| --- | --- | --- | --- | --- |
| `Managed` | any | any | `Managed` | A non-empty canonical value wins. |
| `Removed` | any | any | `Removed` | A non-empty canonical value wins. |
| empty | `Managed` | `Managed` | `Managed` | The managed KServe fallback copies the legacy value. |
| empty | `Managed` | `Removed` | `Removed` | The managed KServe fallback copies the legacy value. |
| empty | `Managed` | empty | empty | The managed KServe fallback copies the empty legacy value. |
| empty | `Removed` or empty | any | empty | Legacy MaaS is ignored unless KServe is `Managed`. |

`Removed` is a non-empty canonical value, whether supplied explicitly or
defaulted after the canonical stanza is present, so it ignores every KServe
legacy value. The schema does not default the parent `modelsAsAService` object:
when that whole stanza is absent, `C` remains empty and the KServe-gated
fallback rows apply.

Evaluate the canonical value, KServe parent state, and legacy MaaS value from
the original v2 source object. Do not base one decision on fields already
mutated by another conversion step.

### Handler behavior that conversion must preserve

The current AI Gateway handler makes three related decisions. Treat these
outputs as the behavioral oracle for every v2 input row:

| Handler output | Current rule |
| --- | --- |
| AI Gateway CR `spec.modelsAsAService.managementState` | Use canonical when non-empty; otherwise copy legacy MaaS only when KServe is `Managed`. |
| MaaS submodule readiness/status enabled | Canonical non-empty is enabled only for `Managed`; otherwise it is enabled only when KServe and legacy MaaS are both `Managed`. |
| AI Gateway platform-module state | Preserve a non-empty AI Gateway parent; otherwise synthesize `Managed` only when KServe and legacy MaaS are both `Managed`, then treat every other empty result as `Removed`. |

The converted v3 object, processed by the canonical-only v3 handler, must
produce the same three outputs as the pre-change handler produces directly
from the v2-equivalent object. In particular, canonical `Removed` disables MaaS
even when KServe and legacy MaaS are `Managed`; the independent empty AI
Gateway parent may still be synthesized to `Managed` in that combination.

### V3 to v2

1. Accept only an absent marker or literal `legacy-managed`; reject every
   unknown marker value, including a present empty string.
2. Copy current canonical MaaS and AI Gateway parent to v2. Their migrated
   values remain; do not restore original `C`, parent `A`, or stanza absence.
3. Set deprecated `kserve.modelsAsService.managementState` (`L`) to `Managed`
   iff the marker is present, otherwise `Removed`, including for original empty
   legacy state. No projection snapshot is stored or compared.
4. Keep the independent KServe parent unchanged and consume the reserved marker
   on the v2 output. Preserve unrelated fields and annotations. A subsequent
   forward conversion resets the marker from current visible legacy `L`.

### Existing v2 CEL contract

Keep the CEL transition validation attached to v2
`kserve.modelsAsService`. Warning removal must not weaken it:

| Operation or transition | Result |
| --- | --- |
| Create with legacy `Managed` | Allowed |
| `Managed -> Managed` | Allowed |
| `Managed -> Removed` | Allowed |
| `Removed -> Removed` | Allowed |
| `Removed -> Managed` | Rejected |

The v3 schema has no legacy field, so it has no corresponding field-specific
CEL rule. The converter consumes existing legacy `Managed` values but does not
invoke or duplicate admission validation. A retained marker restores legacy
`Managed`, so unrelated v2 updates can retain it. After marker
retirement, reverse conversion returns legacy `Removed`; the existing CEL rule
then prevents a v2 client from re-enabling that deprecated path.

### Literal marker and admission lifecycle

DEC-024 uses only `conversion.opendatahub.io/maas-v2-state: legacy-managed`.
No JSON payload, versioned encoding, original-value stash, or projection
snapshot is required. Forward conversion resets this single bit of legacy
intent solely from incoming v2 `L=Managed`.

On native v3 `CREATE`, strip supplied reserved metadata. On v3 `UPDATE`, compare
old/new management states of canonical MaaS, KServe parent, and AI Gateway
parent. A change to any of these three states deletes the marker permanently,
including if later reverted. Otherwise use only the `OldObject` marker,
regardless of whether the new object supplies, changes, omits, or deletes it.
An old object without a marker cannot acquire one through a v3 update. Reject
unknown authoritative marker values. Unrelated edits preserve the old marker
and unrelated annotations; canonical presence is not a separate comparison.

### Accepted normalization and shared types

Reuse the existing `componentApi` AI Gateway and canonical value types in both
API versions. No canonical pointer and no duplicated v2/v3 AI Gateway wrappers
are permitted. Preserve existing OpenAPI defaults and validation, the v2
baseline, and shared/internal module schemas. Only the approved legacy v3
KServe removal changes OpenAPI.

On `v2 -> v3 -> v2`, canonical `C` and AI Gateway parent `A` stay projected,
including a parent synthesized as `Managed`. Original C/A and canonical absence
are not restored. Legacy `Managed` returns via the marker; legacy `Removed`
and empty both return as `Removed`. Required tests use explicit expected
normalized fixtures instead of exact source equality for these accepted cases.
Test schema-defaulted inputs separately from raw typed conversion values.

### Implemented behavior examples

The table shows direct conversion before API-server defaults. `C` is canonical
AI Gateway MaaS, `K` is the KServe parent, `L` is deprecated KServe MaaS, and
`A` is the AI Gateway parent. `M` means `Managed`, `R` means `Removed`, and `∅`
means an empty state. The final column is the deprecated `L` seen after reading
the resulting v3 object through v2.

| v2 C / K / L / A | v3 C / A | v3 marker | v2 read L |
| --- | --- | --- | --- |
| `∅ / M / M / ∅` | `M / M` | `legacy-managed` | `M` |
| `R / M / M / ∅` | `R / M` | `legacy-managed` | `M` |
| `∅ / R / M / ∅` | `∅ / ∅` | `legacy-managed` | `M` |
| `∅ / M / R / ∅` | `R / ∅` | absent | `R` |
| `∅ / M / ∅ / ∅` | `∅ / ∅` | absent | `R` |
| `M / M / R / R` | `M / R` | absent | `R` |

The marker follows the visible legacy `L`, even when canonical `C` wins or
KServe is not managed. Empty legacy `L` normalizes to `Removed` on the v2 read;
migrated canonical and AI Gateway parent values stay in place.

| Subsequent write | Marker after admission/conversion | Legacy L on v2 read |
| --- | --- | --- |
| Native v3 create supplies a marker | stripped | `Removed` |
| Unrelated v3 spec or metadata edit | restored from old v3 object | `Managed` if old marker was present |
| V3 status-subresource update | unchanged in storage | `Managed` if marker was present |
| V3 changes canonical MaaS, KServe parent, or AI Gateway parent | cleared permanently | `Removed` |
| V3 later reverts that state | remains absent | `Removed` |
| V2 changes legacy `Managed` to `Removed` | reset from current v2 L; absent | `Removed` |

For example, start with a v2 DSC whose KServe parent and legacy MaaS are
`Managed`, while canonical MaaS and the AI Gateway parent are empty. A v3 read
shows canonical MaaS and its parent as `Managed`, plus the `legacy-managed`
marker; a v2 read still shows legacy `Managed`. Change canonical MaaS to
`Removed` through v3: admission clears the marker, and v2 now reads legacy
`Removed`. Changing canonical MaaS back to `Managed` does not restore the
marker. The v2 CEL rule then rejects an attempt to set legacy MaaS back to
`Managed`.
