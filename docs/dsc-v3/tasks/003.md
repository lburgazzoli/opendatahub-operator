# DSC-V3-003: Freeze the Data contract

## Lifecycle

Before work, read `../development.md`, `../decisions.md`, `../PLAN.md`, and
`../TASKS.md`, then update this front matter and Outcomes. Record accepted
decisions in `../decisions.md` before using them. Leave the task blocked, with
specific open questions, if owners have not approved a complete contract. Set
completion dates only after all deliverables and checks below are satisfied.

## Objective

Freeze the v3 Data grouping and the v2 compatibility contract for Feature Store
and Data Registry. This is a decision task; implementation belongs to
DSC-V3-006 and DSC-V3-009.

## Current and proposed shapes

V2 currently exposes only Feast lifecycle state. The latest unapproved
compatibility proposal adds a Data Registry child:

```yaml
components:
  feastoperator:
    managementState: Managed
    dataRegistry:
      managementState: Managed
```

The latest unapproved v3 proposal is:

```yaml
components:
  data:
    featureStore:
      managementState: Managed
    dataRegistry:
      managementState: Managed
```

An older proposal gave `data` a parent management state whose `Removed` value
overrode its children. The conflict must be explicitly resolved. DEC-012
excludes Data Connection Hub, and DEC-011 keeps the internal Data/Feast CR,
GVK, and module metadata unchanged for 3.6.

The existing Feast module is enabled from `feastoperator.managementState`.
Its internal CR currently projects external-OIDC issuer configuration but no
Feature Store/Data Registry child lifecycle.

## Required decision

Obtain and record owner approval for:

1. Exact v2 compatibility and v3 YAML/JSON/Go shapes, including whether `data`
   is structural or has a parent management state.
2. Independent and combined behavior for both children in `Managed`,
   `Removed`, empty, and absent states; empty is effectively `Removed`.
3. Shared-operator enablement and cleanup rules when zero, one, or both
   children are managed.
4. Exact status fields, conditions, readiness aggregation, defaults,
   validation, warnings, immutability, and update behavior.
5. Complete v2 -> v3 and v3 -> v2 mappings, including a v2
   read-modify-write.
6. Whether explicit v2 fields represent every v3 value. Approve an annotation
   stash only if a final value is demonstrably unrepresentable, and define its
   key, lifecycle, conflict precedence, and cleanup.
