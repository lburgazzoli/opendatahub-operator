# DSC-V3-002: Freeze the Dashboard v3 contract

## Lifecycle

On start, read `../development.md`, `../decisions.md`, `../PLAN.md`, and
`../TASKS.md`; set `status: in_progress`, `start_date`, `assignee`, and
`last_updated`; and record the branch, commit, and pre-existing changes under
Outcomes. If owner input is unavailable, keep `status: blocked` and record the
exact unanswered questions. On completion, record the accepted decision in
`../decisions.md` before updating summaries elsewhere, fill Outcomes, and set
`status: completed`, `end_date`, and `last_updated`.

## Objective

Produce the exact public v3 Dashboard spec, status, condition, admission, and
v2 conversion contract. This task makes decisions only; it does not modify Go
types or handlers.

## Existing contract and behavior

- V2 has `components.dashboard.managementState` for the core Dashboard and
  `components.dashboard.maasConsumerPortal.managementState` for the portal.
- The portal currently defaults to `Removed`; empty management state has the
  effective meaning `Removed` under DEC-010.
- `internal/controller/modules/dashboard/handler.go` enables the shared
  operator when either core or portal is managed, projects namespaces and
  gateway data, and mirrors `MaaSConsumerPortalAvailable` into DSC status.
- One proposal retains the top-level state. Another makes core and portal
  independent children under a structural `dashboard` group.
- `openshiftAI` was rejected as non-portable feedback; `maasCustomerPortal`
  was challenged because the application also serves administrators. `core`
  and `modelsAsAServicePortal` are suggestions, not accepted names.

## Required decision

Obtain owner approval and record one decision containing:

1. Exact v3 YAML paths, JSON names, Go field/type names, and descriptions for
   the core Dashboard and portal.
2. Whether `dashboard` has its own management state or is only a structural
   parent, plus all valid independent child-state combinations.
3. Exact v3 status paths and condition type names, aggregation, readiness, and
   removal behavior.
4. Defaults, empty/absent semantics, validations, warnings, immutability, and
   update rules.
5. Field-by-field v2 -> v3 and v3 -> v2 mappings for spec, status, and
   conditions, including preservation through a v2 read-modify-write.
6. Expected behavior for `Managed`, `Removed`, empty, absent, and conflicting
   legacy inputs.

The decision must contain final values rather than “TBD,” alternatives, or
provisional examples. Preserve DEC-003, DEC-007, DEC-010, and DEC-014.
